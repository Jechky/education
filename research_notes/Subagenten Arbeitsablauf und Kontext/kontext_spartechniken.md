# Context-saving techniques for AI agents that build LaTeX → PDF, inspect rendered pages, and verify files

All sources accessed 2026-10-02. Labels: **[official]** = Anthropic docs/engineering blog or the tool's own manual; **[community]** = third-party mirror/blog. Numbers labeled "computed" were worked out by the researcher using the official formula and reference implementation (Python, run locally), not quoted from a source.

## 1. Image token costs for Claude vision → sensible render DPI for page checks vs. detail crops

### Takeaway
The current official formula is patch-based: **tokens = ⌈width/28⌉ × ⌈height/28⌉** (≈ width×height/784; the older docs said width×height/750). Claude 4.7+ models allow up to 2576 px long edge / 4784 visual tokens; older models cap at 1568 px / 1568 tokens and downscale anything larger. An A4 page costs about **468 tokens at 60 dpi, 1,260 at 100 dpi, and 2,835 at 150 dpi** (high-res tier; computed). On the standard tier anything above ~112 dpi is downscaled to 924×1307 px (~1,551 tokens), so the extra resolution is wasted. Use ~100 dpi for whole-page layout checks and render small, higher-dpi crops for detail.

### Cited Findings
- **[official]** "Each patch is a 28×28-pixel block of the image, referred to as a visual token. An image, therefore, costs `⌈width / 28⌉ × ⌈height / 28⌉` visual tokens." — [Claude Docs: Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[official]** Resolution tiers: "High-resolution | Claude 4.7 and later models | 2576 px | 4784" tokens; "Standard | All other models | 1568 px | 1568" tokens. "High-resolution support is automatic on the listed models and requires no beta header." — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[official]** Example costs from the table: 200×200 → 64 tokens; 1000×1000 → 1296; 1092×1092 → 1521; 1920×1080 → 1560 (standard tier, downsized to 1456×819) vs. 2691 (high-res tier, not resized); 3840×2160 → 4784 (high-res, downsized to 2576×1449). — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[official]** "High-resolution images can use up to roughly three times more visual tokens than the same image on a standard-tier model. If you don't need the additional fidelity … downsample images before sending to control token costs." — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[official]** Price example: at Opus 5's $5/M input tokens (high-res tier), a 1000×1000 image costs about $6.48 per thousand images. — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[official]** Hard limits: max 8000×8000 px per image. If a request has more than 20 images, a stricter per-image limit applies ("resize each image so that neither dimension exceeds 2000 px, or keep the request to 20 or fewer image and document blocks"). Maximum 100 images per request for 200k-context models and 600 otherwise. Maximum 10 MB per image (base64) on the direct API. — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[official]** Resize rule: Claude finds "the largest aspect-preserving size" that satisfies both the edge limit and the visual-token limit. "For nearly all photos and screenshots, the visual token limit is what determines the final size." — [Vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)
- **[official]** A4 example from the docs: "an A4 page scanned at 130 DPI is 1075×1520 pixels: both sides are under 1568 px, but it costs `39 × 55 = 2145` visual tokens, so Claude resizes it to 924×1307" on the standard tier. A high-res-tier model does not resize it (2145 < 4784). Images are then padded to multiples of 28 px. — [Vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)
- **[official]** "Small elements lose precision when an image is downscaled: for fine targets, crop the region of interest and send the crop … or use a high-resolution-tier model." — [Vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)
- **[official]** Quality guidance: "If the image contains important text, make sure it's legible and not too small. Avoid cropping out key visual context solely to enlarge the text." Heavy JPEG compression "can make text difficult to read." Claude "might hallucinate or make mistakes when interpreting low-quality, rotated, or very small images under 200 pixels." — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[official]** Images persist in history: "Claude has access to every image from earlier turns". Each request resends the full conversation history, including images. — [Vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[official]** Claude Code Read tool: "Claude Code resizes and recompresses large images to fit the model's image size limits before sending them … an image that is still larger than 500KB after that resize is re-encoded as a JPEG at reduced quality with its pixel dimensions unchanged. If Claude misses fine pixel-level detail in a large image, ask it to crop the region of interest first, for example with ImageMagick via Bash." — [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)
- **[official]** Claude Code reads PDFs longer than 10 pages "in ranges with a `pages` parameter … up to 20 pages at a time. Page-range reads render pages with `pdftoppm` from poppler-utils." — [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)
- **[official]** PDF upload cost (API): "Each page typically uses 1,500–3,000 tokens per page depending on content density" for text, and "Because each page is converted into an image, the same image-based cost calculations are applied". PDF pages "are rasterized to images server-side at dimensions you don't control." — [PDF support](https://platform.claude.com/docs/en/build-with-claude/pdf-support); [Vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)
- **[official]** pdftoppm options: `-r` sets resolution in DPI ("The default is 150 DPI"). `-f`/`-l` set first/last page. `-scale-to N` fits the long side to N px. `-x`/`-y`/`-W`/`-H` set a crop area in pixels. `-png`, `-jpeg`, `-jpegopt quality`, `-gray`, `-mono`, and `-singlefile` are also available. — [pdftoppm(1) man page](https://manpages.debian.org/testing/poppler-utils/pdftoppm.1.en.html)
- **[community]** Older formula: "tokens = (width px * height px)/750", with a recommendation to resize to "no more than 1.15 megapixels (and within 1568 pixels in both dimensions)". The older max sizes were 1092×1092 (1:1) and 951×1268 (3:4), about 1,600 tokens each. — [unofficial mirror of earlier Claude vision docs](https://claude.yourdocs.dev/docs/build-with-claude/vision). This is **superseded** by the 28-px patch formula on the [current official page](https://platform.claude.com/docs/en/build-with-claude/vision). The two formulas agree to within a few percent for small and medium images.

### Inferences
- **Computed A4 costs** (210×297 mm, using pdftoppm pixel sizes; official formula and reference implementation):

| DPI | Pixels | Tokens (high-res tier, Claude 4.7+) | Tokens (standard tier) | Old /750 formula |
|---|---|---|---|---|
| 50 | 414×585 | 315 | 315 | ~323 |
| 60 | 497×702 | **468** | 468 | ~465 |
| 72 | 596×842 | 682 | 682 | ~669 |
| 100 | 827×1170 | **1,260** | 1,260 | ~1,290 |
| 110 | 910×1287 | 1,518 | 1,518 | ~1,562 |
| 120 | 993×1404 | 1,836 | 1,551 (downscaled to 924×1307) | ~1,859 |
| 150 | 1241×1754 | **2,835** | 1,551 (downscaled to 924×1306) | ~2,902 |
| 200 | 1654×2339 | 4,756 (downscaled to 1624×2296) | 1,551 | ~5,158 |
| 300 | 2481×3508 | 4,756 (downscaled) | 1,551 | ~11,604 |

- **Effective ceiling:** On the standard tier, an A4 page never exceeds about 924×1307 px (about 112 dpi equivalent, about 1,551 tokens). On the high-res tier, the ceiling is about 1624×2296 px (about 196 dpi, about 4,756 tokens). Rendering above these values wastes render time and file size and gains nothing.
- **Recommended settings for a verification agent** (derived from the facts above):
  - **Overview/layout check** (page breaks, floats, overall look): `pdftoppm -f N -l N -r 60 -png` (~470 tokens per page). Use `-r 72` to `-r 100` (~680 to 1,260 tokens) if body text needs to be roughly legible.
  - **Readability/typography check of a whole page:** `-r 100` (~1,260 tokens). This is the best value: below the standard-tier cap, so the model sees exactly what you render.
  - **Detail crop** (formula, table, overfull line, figure label): render at 150–200 dpi and crop with `-x -y -W -H`. Computed examples: a 1000×500 px crop costs 648 tokens, a full-width 1240×300 px strip at 150 dpi costs 495 tokens, and an 800×400 crop costs 435 tokens. That is far cheaper than a full 150-dpi page (2,835) and sharper. Keep crops above 200 px per side (see the docs' small-image warning).
  - Prefer PNG for text pages, and `-gray` to cut file size. That helps stay under Claude Code's 500 KB JPEG-recompression threshold, which could otherwise blur small text.
  - **Avoid Reading the PDF itself** for a single-page check. The API PDF path adds about 1,500–3,000 text tokens per page on top of image cost, and you cannot control the rasterization DPI. Render the one page you need with pdftoppm and Read the PNG instead.
- **Images are sticky:** they stay in context, and are resent every turn, until compaction or clearing. Doing visual checks inside a short-lived subagent that returns a text verdict keeps image tokens out of the main agent entirely.
- For text-content verification (spelling, presence of a heading or number), text extraction (e.g., poppler's `pdftotext -f N -l N -layout`) is likely far cheaper than an image. This is not quantified in the sources and pdftotext was not cited; verify locally.

### Gaps
- No official statement on whether Claude Code's Read tool downsizes images to the standard or high-res limits for a given model. The docs say only "to fit the model's image size limits".
- No public data on how much visual-check accuracy drops at 60 vs. 100 vs. 150 dpi for typeset LaTeX text. The DPI recommendations above are reasoning, not measurements.
- pdftoppm's exact pixel rounding (e.g., 1240 vs. 1241 px at 150 dpi) was not verified from documentation. Token differences are at most one patch row or column.

## 2. Reading files efficiently and avoiding verbose build output

### Takeaway
Claude Code already caps tool output: Bash shows about 30,000 characters inline (failures about 10,000), longer output goes to a file plus a 2,000-character preview, and MCP output is capped at 25,000 tokens. Even so, each read or build log the agent keeps costs tokens on every later turn. Use targeted reads (Grep, offset/limit), structured or concise output, and silent LaTeX builds followed by a grep of the .log, or texfot.

### Cited Findings
- **[official]** "For Claude Code, we restrict tool responses to 25,000 tokens by default." Tool authors should "implement some combination of pagination, range selection, filtering, and/or truncation with sensible default parameter values", and steer agents toward "many small and targeted searches instead of a single, broad search." — [Anthropic Engineering: Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- **[official]** A concise vs. detailed `response_format` example: a detailed response was 206 tokens and the concise one 72 tokens (≈65% fewer). — [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- **[official]** Bash output limits: a valid result is shown "Inline up to roughly 30,000 characters by default; past that, the path of a file saved to the session directory … plus a preview of up to the first 2,000 characters, and Claude reads or searches the file when it needs the rest". A failed result is shown "Inline up to roughly 10,000 characters; past that, a head-and-tail excerpt". — [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)
- **[official]** `BASH_MAX_OUTPUT_LENGTH` defaults to 30000 characters (maximum 150000). The `bashOutputMaxChars` setting allows up to 128,000 characters inline. — [Claude Code env vars](https://code.claude.com/docs/en/env-vars); [tools reference](https://code.claude.com/docs/en/tools-reference)
- **[official]** Read tool: "When a whole-file read exceeds the token limit, Read returns the first page with a `PARTIAL view` notice that tells Claude how much of the file it received and how to read more with `offset` and `limit`." `CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS` overrides the file-read token limit. — [tools reference](https://code.claude.com/docs/en/tools-reference); [env vars](https://code.claude.com/docs/en/env-vars)
- **[official]** Glob results are "capped at 100 files". Grep (ripgrep-based) has `content`, `count` and files-only modes with `head_limit`/`offset`. — [tools reference](https://code.claude.com/docs/en/tools-reference)
- **[official]** MCP output: a warning at 10,000 tokens and a default maximum of 25,000 tokens (`MAX_MCP_OUTPUT_TOKENS`). A larger result with no images is saved to a file in the session's `tool-results` directory and replaced by its path. — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- **[official]** Illustrative per-action costs from the Claude Code context-window walkthrough: reading `auth.ts` costs 2,400 tokens, a grep costs 600, and `npm test` output costs 1,200. "You see the command ran, not the full output." — [Claude Code: Explore the context window](https://code.claude.com/docs/en/context-window)
- **[official]** Hooks: output a PostToolUse hook returns via `hookSpecificOutput.additionalContext` "enters Claude's context. Plain stdout on exit 0 does not." — [Explore the context window](https://code.claude.com/docs/en/context-window)
- **[official]** "CLI tools are the most context-efficient way to interact with external services." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[official]** latexmk: `-silent` / `-quiet` mean "Run commands silently, i.e., with options that reduce the amount of diagnostics generated". The default `$pdflatex_silent_switch` is `-interaction=batchmode`. `-logfilewarninglist` gives "a list of warnings about undefined citations and references (unless silent mode is on)". `-f` forces processing to continue despite errors. `-outdir`/`-auxdir` move output and aux files. — [latexmk(1) man page](https://manpages.debian.org/testing/latexmk/latexmk.1.en.html)
- **[official]** TeX engine flags: `-interaction` accepts batchmode/nonstopmode/scrollmode/errorstopmode. `-halt-on-error` means "Exit with an error code when an error is encountered". `-file-line-error` means "Print error messages in the form file:line:error". — [tex(1) man page](https://manpages.debian.org/testing/texlive-binaries/tex.1.en.html)
- **[official]** texfot (by Karl Berry) "invokes a TeX command while filtering the online output for 'interesting' messages", keeping "error messages, overfull and underfull boxes, undefined citations, missing characters from fonts, etc." Options include `--quiet`, `--ignore regexp`, `--tee file` (unfiltered copy, default `$TMPDIR/fot.uid`) and `--no-stderr`. Usage: `texfot pdflatex file.tex`. — [texfot(1) man page](https://manpages.debian.org/testing/texlive-extra-utils/texfot.1.en.html); [CTAN texfot](https://ctan.org/pkg/texfot)

### Inferences
- **Build recipe for a builder agent** (derived from the flags above; not taken from a single source):
  ```bash
  latexmk -pdf -silent -halt-on-error -file-line-error -outdir=build main.tex >/dev/null 2>&1; echo "exit=$?"
  grep -nE '^[^ ]+:[0-9]+:|^!|Overfull|Undefined|undefined|Rerun|Missing character' build/main.log | head -40
  ```
  An alternative is `texfot --quiet pdflatex -interaction=nonstopmode -halt-on-error -file-line-error main.tex`, with `--ignore '^Underfull'` if underfull boxes are noise. Either way the agent sees a few dozen lines instead of a multi-thousand-line pdflatex transcript. The full log stays on disk for targeted reads.
- Count first, then read: e.g., `grep -c Overfull build/main.log`, then `grep -n -A2 Overfull … | head`.
- **File reading:** use Grep or a heading outline before full reads, e.g., `grep -nE '\\(part|chapter|section|subsection)\{' *.tex` yields a table of contents for a few hundred tokens. Then Read with offset/limit around the line numbers. For handoff docs, read only the needed section.
- Do not rely on the 30k-character cap as a budget. 30,000 characters per command is still large (an estimated several thousand tokens); filter at the source.
- PostToolUse hooks that run a silent build or lint and print nothing on success add no context. Report via `additionalContext` only on failure.

### Gaps
- The exact default Read-tool token limit and default line count are not stated on the public tools-reference page. The in-product tool description says "up to 2000 lines by default", but there is no public URL for that.
- No community measurement was found of tokens saved by latexmk `-silent` or texfot vs. raw pdflatex output for a typical document.
- No source quantified a chars-per-token ratio for LaTeX logs, so the character limits above were not converted to tokens.

## 3. Keeping CLAUDE.md and handoff docs lean; progressive disclosure (skills, @imports, rules)

### Takeaway
The official target is under 200 lines per CLAUDE.md. Only "every-session" facts belong there. Procedures and part-specific knowledge go into skills (only name and description load until invoked; SKILL.md under 500 lines; reference files load on demand) or path-scoped `.claude/rules/`. `@imports` organize content but **do not** reduce context cost.

### Cited Findings
- **[official]** "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." "Imports help you organize a long file but don't reduce its context cost, because imported files also load at launch." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- **[official]** "Keep it to facts Claude should hold in every session: build commands, conventions, project layout, 'always do X' rules. If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead." — [memory docs](https://code.claude.com/docs/en/memory)
- **[official]** Include/exclude table. Include: bash commands Claude can't guess, style rules that differ from defaults, test instructions, repo etiquette, architectural decisions, env quirks, gotchas. Exclude: what Claude can infer from code, standard conventions, "Detailed API documentation (link to docs instead)", frequently changing info, long tutorials, file-by-file descriptions. Test: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[official]** `@path` imports: they are "expanded and loaded into context at launch". Recursive imports have "a maximum depth of four hops". — [memory docs](https://code.claude.com/docs/en/memory)
- **[official]** Subdirectory CLAUDE.md files "load on demand when Claude reads files in those directories". `.claude/rules/` files with `paths:` frontmatter "only load into context when Claude works with matching files". — [memory docs](https://code.claude.com/docs/en/memory)
- **[official]** "Block-level HTML comments (`<!-- maintainer notes -->`) in CLAUDE.md files are stripped before the content is injected into Claude's context." — [memory docs](https://code.claude.com/docs/en/memory)
- **[official]** Auto memory: "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded". Topic files are read on demand. A CLAUDE.md of up to 4 MiB loads in full, but "Shorter files produce better adherence." — [memory docs](https://code.claude.com/docs/en/memory)
- **[official]** Illustrative startup costs: system prompt 4,200 tokens, auto memory 680, environment info 280, deferred MCP tool names 120, skill descriptions 450, user CLAUDE.md 320, project CLAUDE.md 1,800. — [Explore the context window](https://code.claude.com/docs/en/context-window)
- **[official]** Skills: "skill descriptions are loaded into context … but full skill content only loads when invoked". The listing budget "scales at 1% of the model's context window". "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files." "Once a skill loads, its content stays in context across turns, so every line is a recurring token cost." `disable-model-invocation: true` takes the description out of context entirely. `context: fork` runs the skill in an isolated subagent. — [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- **[official]** After compaction, invoked skills are re-attached, "keeping the first 5,000 tokens of each", with a combined budget of 25,000 tokens. "Truncation keeps the start of the file, so put the most important instructions near the top of `SKILL.md`." — [skills docs](https://code.claude.com/docs/en/skills); [Explore the context window](https://code.claude.com/docs/en/context-window)
- **[official]** MCP tool schemas are deferred by default (only names load; schemas load via tool search). `ENABLE_TOOL_SEARCH=auto` loads schemas upfront only "when they fit within 10% of the context window". — [Explore the context window](https://code.claude.com/docs/en/context-window)
- **[official]** "Structured note-taking": agents write external notes (e.g., NOTES.md) to keep memory across context resets. Agents should keep "lightweight identifiers (file paths, stored queries, web links, etc.)" and retrieve data just in time. — [Anthropic Engineering: Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **[official]** Write specs that are "self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step", then "start a fresh session to execute it." — [best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- For a LaTeX pipeline: CLAUDE.md (under 200 lines; ideally well under 100 for subagents, which also load it) holds the build command, render command, directory layout and a few hard rules. Template conventions, the visual-check checklist and LaTeX error playbooks go into skills or path-scoped rules (e.g., `paths: ["**/*.tex"]`). Long reference material (class options, style guide) goes in skill supporting files that are linked, not imported.
- Handoff docs between agents should be indexes: status, decisions, and **paths** to artifacts and logs, not pasted content. The receiving agent reads specific sections just in time.
- Because each subagent loads the full CLAUDE.md hierarchy (see section 4), a bloated CLAUDE.md costs once per subagent spawn. Leanness matters more in multi-agent setups.

### Gaps
- No official token target for handoff documents. The 200-line guidance applies to CLAUDE.md only, and the 1,000–2,000-token guidance (section 4) to subagent summaries.
- No quantitative study was found linking CLAUDE.md length to adherence. The docs assert it qualitatively.

## 4. Subagent return values: compact summaries, artifacts on disk, pass paths

### Takeaway
Subagents run in a separate context window and only their final message returns. Anthropic's guidance is a "condensed, distilled summary … often 1,000–2,000 tokens", and the Claude Code walkthrough shows 6,100 tokens of reads collapsing into a 420-token result. Ask for a structured, length-capped report, have bulky outputs (logs, renders, diffs) written to disk, and return paths.

### Cited Findings
- **[official]** "Specialized sub-agents … return only a condensed, distilled summary of its work (often 1,000-2,000 tokens)". — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **[official]** "Only the subagent's final text response comes back to your context, plus a small metadata trailer with token counts and duration. The subagent read 6,100 tokens of files. You got a 420-token result. That's the context savings." — [Explore the context window](https://code.claude.com/docs/en/context-window)
- **[official]** "One of the most effective uses for subagents is isolating operations that produce large amounts of output. Running tests, fetching documentation, or processing log files can consume significant context." Example prompt: "Use a subagent to run the test suite and report only the failing tests with their error messages". — [Claude Code subagents docs](https://code.claude.com/docs/en/sub-agents)
- **[official]** A non-fork subagent starts with its own system prompt, the task message, **all CLAUDE.md levels**, git status, and any preloaded skills. It does not get conversation history or the main session's auto memory. "The built-in Explore and Plan agents skip [CLAUDE.md] for a smaller context." — [subagents docs](https://code.claude.com/docs/en/sub-agents); [Explore the context window](https://code.claude.com/docs/en/context-window)
- **[official]** Forks inherit the full parent conversation. "its first request reuses the parent's prompt cache. This makes forking cheaper than spawning a fresh subagent for tasks that need the same context." Subagent descriptions "take up context, so keep them short." Costs can be controlled "by routing tasks to faster, cheaper models like Haiku". — [subagents docs](https://code.claude.com/docs/en/sub-agents)
- **[official]** "Delegate research with 'use subagents to investigate X'. They explore in a separate context." A verification subagent "sees only the diff and the criteria you give it". Tell reviewers "to flag only gaps that affect correctness or the stated requirements". — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- **[official]** Non-interactive fan-out pattern: `claude -p "Migrate $file … Return OK or FAIL."`, i.e., force a minimal return value. — [best practices](https://code.claude.com/docs/en/best-practices)
- **[official]** Tools should return "high signal information" and meaningful identifiers rather than low-level technical IDs. A concise format used about a third of the tokens of a detailed one (72 vs. 206). — [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

### Inferences
- **Return contract template** for build and verify subagents (derived): "Return ≤15 lines: `STATUS: PASS|FAIL`; `PDF: <path>`; `PAGES: n`; `ISSUES:` up to 5 bullets with `file:line` or `page N, region`; `ARTIFACTS: <paths to log/PNGs/diff>`. No log excerpts over 5 lines; no images." This fits well within the 1,000–2,000-token guidance (likely under 300 tokens).
- **Images stay in the verifier:** the visual-check subagent renders and reads PNGs (about 470–2,800 tokens each, section 1) and returns text only. The orchestrator never pays image tokens.
- Store everything bulky on disk (build/main.log, renders/page-03.png, notes/verify-report.md) and pass paths between agents. This is Anthropic's "lightweight identifiers" pattern applied to multi-agent handoffs.
- Spawn cost matters: every fresh subagent re-pays the system prompt plus CLAUDE.md. For many tiny checks, batch them in one subagent, use a fork (cache reuse), or use the Explore agent (skips CLAUDE.md) for read-only lookups.

### Gaps
- No official numeric cap on subagent result size in Claude Code was found. The 1,000–2,000-token figure is descriptive ("often"), not a limit.
- No community measurements were found comparing free-form vs. structured subagent reports in tokens or quality.

## 5. Other levers: context editing/clearing, compaction, avoiding repeated reads, prompt caching

### Takeaway
On the API, server-side **context editing** (`clear_tool_uses_20250919`) drops old tool results. Defaults: trigger at 100k input tokens, keep the last 3 tool uses. Anthropic reported **84% fewer tokens** in a 100-turn eval and +29% (+39% with the memory tool) task performance. In Claude Code, use `/clear` between tasks, `/compact <focus>`, and `/btw`. Know what survives compaction: root CLAUDE.md, up to 5 recent files (≤5,000 tokens each), and skill bodies capped at 5k each and 25k total. Prompt caching makes a stable prefix cheap (reads cost 0.1× or less), but clearing content or adding/removing images invalidates the messages cache.

### Inferences
- **Avoiding repeated reads:** after a builder edits a .tex file, the verifier needs only the diff or line ranges, not the whole file again. Pass `file:line` ranges in handoffs. After compaction Claude Code re-reads at most 5 files, and files over 5k tokens come back as paths only, so splitting large .tex sources into chapter files (`\input`) keeps each re-read cheap and targeted.
- **Re-rendering loop:** each verify iteration that adds a new page image adds about 470–2,800 tokens, which stay in history. In a single long-running agent, that argues for (a) rendering only changed pages, (b) using low DPI for "did it change?" checks, and (c) delegating image checks to fresh subagents. On the API, context editing with `keep` small also helps. Whether it clears image tool results is not stated (see Gaps).
- Cache-friendliness: keep system prompt, tools and CLAUDE.md stable across runs so the prefix caches. Avoid mid-session tool or MCP changes, which invalidate everything. Clearing old tool results breaks the cache once, so set `clear_at_least` large enough to be worth it.

### Gaps
- The context-editing docs do not say explicitly whether image content inside `tool_result` blocks is cleared by `clear_tool_uses_20250919`. The researcher assumes yes, since whole tool results are cleared, but this is unconfirmed.
- The 84%/29%/39% figures come from Anthropic's own internal evals (web search, agentic tasks). No independent replication was found, and no LaTeX/document-build-specific measurements exist.
- The default auto-compact threshold percentages per model live on a separate page ([model-config](https://code.claude.com/docs/en/model-config#default-auto-compact-thresholds)) that was not fetched.
- Practitioner blogs with measured savings for document-build agents (LaTeX → PDF → vision check) were not found within the search budget. The community evidence base for these exact workflows appears thin. The only community source used here is an unofficial docs mirror for the old /750 formula.
